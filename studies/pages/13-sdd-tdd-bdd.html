📐 SDD, TDD e BDD: dirigir a IA por especificação (2026)

No artigo 12 você aprendeu a operar o agente. Agora vem a pergunta que decide se o código gerado presta: o que é “pronto”? A IA escreve Kotlin que compila e parece certo — mas “parece” não é “é”. Sem um alvo escrito antes, o loop gira agradando você em vez de acertar. As três siglas deste artigo — SDD, TDD, BDD — são três formas de fixar esse alvo antes de a IA digitar. Não competem: encadeiam.

🔗 Fio condutor: este é o par teórico do artigo 12. Lá, o squad de um dev só passava um bastão (PLANO.md → SPEC.md → código → REVIEW.md); esse bastão é SDD. Aqui a gente formaliza, soma TDD e BDD, e mostra por que teste é a melhor coleira de alucinação que existe.

A pergunta que trava a IA

Peça “faça a tela de login” e você recebe uma das mil telas possíveis — a que o modelo achou mais provável, não a que o produto precisa. O antídoto é sempre o mesmo: escrever o critério de aceite antes. As três metodologias fazem isso em níveis diferentes.

Parte 1 · SDD — dirigir por especificação

Spec-Driven Development: o humano escreve a especificação; a IA a executa. O código deixa de ser a fonte da verdade — a spec é. É exatamente o fluxo do artigo 12: o PO recorta o problema, o Tech trava o “como”, e só então o Dev implementa obedecendo ao documento.

Uma boa spec para a IA tem quatro coisas: escopo (e o fora de escopo, honesto), contrato (assinaturas, estados, erros), dados e critérios de pronto. Com ela no disco, o prompt fica curto e o agente não precisa adivinhar.

# SPEC — Recuperar senha (MVP)

## Escopo
- Enviar link de reset por e-mail. FORA: SMS, perguntas de segurança.

## Contrato (domínio, sem Android)
interface AuthRepository { suspend fun enviarReset(email: String): Result<Unit> }
class SolicitarReset(repo): suspend operator fun invoke(email): Result<Unit>

## Estados da tela (MVI)
data class ResetUiState(carregando, enviado, erro: String?)

## Critérios de pronto
- E-mail inválido → erro local, NÃO chama o repositório.
- Sucesso → estado `enviado = true`.
- Falha de rede → `erro` preenchido, botão volta a habilitar.

🔒 Visão Specialist: a versão moderna do SDD tem ferramenta (o plan mode do próprio agente, kits como o Spec-Kit). Mas o princípio não depende de tooling: uma spec revisável no disco é o que separa “a IA fez algo” de “a IA fez o que combinamos”. Revisar a spec de 50 linhas é barato; revisar 500 linhas de Kotlin depois, não.

Parte 2 · TDD — o teste como coleira da alucinação

Test-Driven Development inverte a ordem intuitiva: o teste vem primeiro. Você escreve um teste que falha (RED), faz o mínimo para passar (GREEN) e então limpa o código com a rede de segurança verde (REFACTOR). Com IA, esse ciclo ganha um superpoder: o teste é um alvo objetivo que o modelo não consegue “contornar com lábia”.

Na prática, você conduz e a IA preenche. Primeiro o teste (o contrato do UseCase da spec):

// RED — escrevo o comportamento esperado; ainda não existe implementação
class SolicitarResetTest {
    private val repo = FakeAuthRepository()
    private val solicitar = SolicitarReset(repo)

    @Test fun `email invalido nao chama o repositorio`() = runTest {
        val r = solicitar("email-sem-arroba")
        assertTrue(r.isFailure)
        assertEquals(0, repo.chamadas)          // nunca tocou a rede
    }
}

Só então o prompt para a IA: “faça SolicitarResetTest passar com o mínimo; não adicione comportamento fora do teste”. O modelo implementa contra um alvo que ou está verde ou não está — sem espaço para plausibilidade.

🔗 Ligação: tudo do artigo 11 vale aqui — runTest + Turbine para o ViewModel, fakes em vez de mocks, domínio puro testado sem Android. TDD é só a ordem em que você escreve; a caixa de ferramentas é a mesma.

⚠️ Pegadinha — deixar a IA escrever teste E código de uma vez: se o mesmo passo gera o teste e a implementação, o teste vira espelho do código (passa sempre, prova nada). Escreva/revise o teste você; deixe a implementação para a IA. O valor do TDD está no teste vir antes e de uma fonte independente.

Parte 3 · BDD — a linguagem única

Behavior-Driven Development sobe um degrau: descreve comportamento na linguagem do negócio, no formato Given-When-Then (Dado-Quando-Então). A frase é a mesma para o PO que aprova, o dev que implementa e a IA que recebe o alvo — acaba a tradução perdida entre “o que o produto pediu” e “o que o código faz”.

O Given-When-Then casa perfeitamente com o Robot Pattern + AAA do artigo 11: Given/And é o arrange, When é a action, Then é o assert. O cenário legível vira teste sem fricção.

@Test fun `total por pessoa divide o item entre participantes`() {
    RachaRobot(compose)
        .arrange { montaMesa(pessoas = 2); adicionaItem(preco = 40.0) }  // Given / And
        .action  { abreTotais() }                                         // When
        .assert  { totalDe("Ana") shouldBe 20.0 }                         // Then
}

No Android, escolha a dose de BDD com cuidado. Você não precisa de Cucumber e arquivos .feature para colher o valor:

NívelComoCusto/benefício
BDD “leve” (recomendado)Nomes de teste e Robots em Given-When-Then; a frase do cenário no @Test.Todo o ganho de legibilidade, zero infra extra.
BDD “formal”Cucumber-Android + .feature em Gherkin, step definitions ligadas a Espresso.Só compensa quando gente não-técnica escreve/lê os cenários.

🧠 Termo — Gherkin & ATDD: Gherkin é a sintaxe Feature/Scenario/Given/When/Then. ATDD (Acceptance-Test-Driven) é o primo do BDD focado no critério de aceite: o teste de aceitação é acordado antes e guia a implementação — o mesmo espírito, ênfase no “aceito/não aceito”.

Parte 4 · Como se encaixam (com IA no meio)

A confusão comum é achar que você escolhe uma. Na verdade cada uma responde a uma pergunta diferente, e num fluxo com IA elas se encadeiam:

SiglaPerguntaNívelArtefato que a IA recebe
SDDO quê e até onde?Produto / arquiteturaSPEC.md revisável
BDDQual comportamento?Feature / linguagemCenário Given-When-Then
TDDEstá correto?Unidade / funçãoTeste que falha

O ciclo de trabalho do dev Android com IA fica assim:

1. SDD  → jaleco de Tech: escreve/revisa SPEC.md (escopo + contrato + critérios)
2. BDD  → traduz os critérios em cenários Given-When-Then (a aceitação)
3. TDD  → para cada cenário, escreve o teste RED; a IA faz passar (GREEN)
4. Refatora com a suíte verde; QA confronta o REVIEW contra a SPEC

🔒 Visão Specialist: você não faz o ritual completo para tudo. Bug isolado? Só TDD (teste que reproduz → correção). Feature nova de produto? SDD para recortar, BDD para os cenários-chave, TDD nas unidades. A régua é o risco: quanto mais caro o erro, mais cedo você escreve o alvo.

Parte 5 · Outros padrões que o especialista soma

SDD/TDD/BDD não vivem sozinhos. Estes padrões se conectam e valem a pena conhecer para conduzir a IA bem:

PadrãoO que traz para o trabalho com IA
DDD (Domain-Driven Design)A linguagem ubíqua — os termos do negócio viram nomes no código e alimentam os cenários BDD. Liga direto ao domínio puro do artigo 09.
Clean / HexagonalFronteiras claras (a Regra da Dependência do artigo 09) dão à IA um alvo pequeno e testável por vez, em vez do app inteiro.
Contract testingFixa o contrato da API (ex.: MockWebServer, Pact) para a IA não “inventar” campos de JSON que o backend não devolve.
Conventional Commits + trunk-basedUm commit por intenção, mensagem padronizada (liga ao artigo 06). Diffs pequenos = revisão possível do código gerado.
Pair programming com IAVocê é o navegador (decide o alvo, revisa), a IA é o motorista (digita). Nunca o contrário.

🔒 Visão Specialist — o fio que une tudo: toda essa lista existe para uma coisa só — reduzir a ambiguidade antes de gerar, e detectar o erro depois de gerar. A IA é rápida no meio (digitar). O valor do especialista está nas pontas: dizer com precisão o que fazer, e provar que o resultado está certo. Metodologia não é burocracia; é o que faz a velocidade da IA render em vez de acumular dívida.
