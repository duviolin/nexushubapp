🎨 Jetpack Compose: a UI como função do estado (2026)

Até aqui a trilha cuidou do chão da UI — desenhar sob as barras (03), dp e densidade (04). Agora entra a ferramenta com que você realmente constrói tela no Android moderno: o Jetpack Compose. Ele troca o velho jeito imperativo (inflar XML, achar View por id e mandar cada mudança na mão) por um jeito declarativo: você descreve como a tela deve ficar para um dado estado, e o Compose se encarrega de atualizar o que mudou. Este artigo vai do básico (composables, layout, Modifier, estado) ao avançado (recomposição, estabilidade, side-effects e performance) — porque é fácil escrever Compose que funciona e difícil escrever Compose que não trava.

🔗 Fio condutor: o 05 · Densidade deu as unidades (dp); aqui você monta a tela com elas. O próximo (07 · Material 3) veste esses composables com o sistema de design, e o 13 · Arquitetura mostra quem alimenta o estado que a tela desenha.

Parte 1 · Declarativo: a virada de chave

No mundo antigo (Views/XML) a UI é um objeto que você muta: textView.text = "Oi", button.isEnabled = false. O bug clássico é a tela e os dados saírem de sincronia — você esqueceu de atualizar um dos dez lugares. No Compose, você não muta a tela: você escreve uma função que, dado o estado, produz a UI. Mudou o estado? O Compose re-executa a função e reconcilia a diferença.

// Imperativo (Views): você descreve os PASSOS de mudança
nomeTextView.text = usuario.nome
avatarImageView.setImageUrl(usuario.foto)
badge.visibility = if (usuario.online) View.VISIBLE else View.GONE

// Declarativo (Compose): você descreve o RESULTADO para aquele estado
@Composable
fun CartaoUsuario(usuario: Usuario) {
    Column {
        Text(usuario.nome)
        Avatar(usuario.foto)
        if (usuario.online) Badge()      // não existe "esconder": ou está na árvore, ou não
    }
}

🧠 Termo — @Composable: uma função anotada que emite UI em vez de retornar valor. Ela não “desenha” na hora: descreve um nó na árvore de UI que o Compose gerencia. Só pode ser chamada de dentro de outra função @Composable.

Parte 2 · Os blocos de construção

Três containers resolvem 90% do layout — e todos empilham por ordem de chamada:

ComposableFazEquivalente mental
Columnempilha os filhos na verticaluma pilha de cima para baixo
Rowalinha os filhos na horizontaluma fila lado a lado
Boxempilha os filhos em camadas (z)um FrameLayout: um sobre o outro
LazyColumn/LazyRowlista que só compõe o que está visívelo RecyclerView, sem boilerplate

O Modifier é o que ajusta tamanho, espaçamento, clique, fundo, borda — encadeado, e a ordem importa (é o padrão Decorator do artigo 14). Sempre receba um Modifier como parâmetro para o chamador poder posicionar seu componente.

@Composable
fun Saudacao(nome: String, modifier: Modifier = Modifier) {   // convenção: modifier é o 1º opcional
    Text(
        text = "Olá, $nome",
        modifier = modifier
            .fillMaxWidth()
            .padding(16.dp)          // afasta ANTES…
            .background(Azul)        // …então pinta só a área interna
            .clickable { /* … */ }
    )
}

// Lista performática: dê uma key estável para o Compose reusar os itens certos
@Composable
fun ListaTarefas(tarefas: List<Tarefa>) {
    LazyColumn {
        items(tarefas, key = { it.id }) { tarefa ->    // key evita recomposição errada ao reordenar
            LinhaTarefa(tarefa)
        }
    }
}

⚠️ Pegadinha: Column (e Row) compõem todos os filhos de uma vez — se a lista for grande, trava. Para listas roláveis use sempre LazyColumn: ela só compõe os itens na viewport. Column com verticalScroll é para conteúdo curto e conhecido.

Parte 3 · Layout: como o Compose mede — e como fazer o complexo

Para ir além de empilhar coisas, você precisa entender como o Compose calcula tamanhos e posições. O modelo é enxuto e é o que torna o layout rápido: as restrições descem, os tamanhos sobem, e mede-se cada nó uma vez só.

🧠 Termo — Constraints: o “orçamento” de espaço que o pai dá ao filho: largura mínima/máxima e altura mínima/máxima. fillMaxWidth() diz “ocupe o máximo”; wrapContentWidth(), “o mínimo que couber”; width(200.dp) fixa os dois. O filho responde com um tamanho dentro desse limite.

Distribuir espaço: arrangement, alignment e weight

Dentro de Row/Column, três eixos resolvem quase todo alinhamento — e o weight reparte o espaço que sobra, como o do XML, mas sem o custo de remedir.

Row(
    horizontalArrangement = Arrangement.spacedBy(8.dp),   // espaço ENTRE os filhos
    verticalAlignment = Alignment.CenterVertically,       // alinhamento no eixo cruzado
) {
    Text("Título", Modifier.weight(1f))     // fica com todo o espaço sobrando…
    Icon(Icons.Default.Star, null)          // …e o ícone só o que precisa
}

Responsivo de verdade: BoxWithConstraints e intrinsics

Quando o layout precisa decidir conforme o espaço, BoxWithConstraints te dá a largura disponível durante a composição — é a peça para telas adaptativas (liga ao 07 · Material e às Window Size Classes do 04). Já os intrinsics respondem “de que tamanho isto gostaria de ser?” sem medir de fato — úteis para, por exemplo, dar a dois textos a mesma altura.

BoxWithConstraints {
    if (maxWidth < 600.dp) ListaEmColuna()      // celular
    else                    ListaEDetalheLado()  // tablet/desktop
}

// intrinsics: o divisor vertical ganha a altura do texto mais alto ao lado
Row(Modifier.height(IntrinsicSize.Min)) {
    Text(esquerda); VerticalDivider(); Text(direita)
}

Layouts complexos: ConstraintLayout & custom Layout

Sim, o ConstraintLayout existe no Compose (dependência androidx.constraintlayout:constraintlayout-compose), com guidelines, barriers e chains como no XML. Mas o motivo nº 1 de usá-lo lá — achatar a hierarquia para não pagar remedições caras — não existe aqui: aninhar Row/Column/Box no Compose é barato (passada única). Então a régua muda: use ConstraintLayout quando ele deixa o código mais legível (muitas relações entre irmãos, alinhar por uma linha-guia percentual, um barrier que segue o mais largo) — não por reflexo do XML.

ConstraintLayout(Modifier.fillMaxWidth()) {
    val (avatar, nome, botao) = createRefs()
    val guia = createGuidelineFromStart(0.5f)                 // linha-guia a 50%
    Avatar(Modifier.constrainAs(avatar) { top.linkTo(parent.top); start.linkTo(parent.start) })
    Text("Ana", Modifier.constrainAs(nome) { start.linkTo(avatar.end, 8.dp); top.linkTo(avatar.top) })
    Button(::seguir, Modifier.constrainAs(botao) { end.linkTo(parent.end); centerVerticallyTo(avatar) })
}

Quando nenhum contêiner pronto serve — um layout radial, um fluxo que quebra por conta, um posicionamento medido — desça para o Layout { } (ou Modifier.layout { } para ajustar um único filho). Você recebe os measurables e as constraints, mede cada filho e os posiciona à mão.

@Composable
fun ColunaSimples(modifier: Modifier = Modifier, content: @Composable () -> Unit) {
    Layout(content, modifier) { measurables, constraints ->
        val filhos = measurables.map { it.measure(constraints) }   // mede cada um (1x!)
        val altura = filhos.sumOf { it.height }
        layout(constraints.maxWidth, altura) {                     // define o tamanho do pai
            var y = 0
            filhos.forEach { it.placeRelative(0, y); y += it.height }   // posiciona empilhando
        }
    }
}

🔒 Visão Specialist: a hierarquia de escolha para layout é: Row/Column/Box → BoxWithConstraints (responsivo) → ConstraintLayout (clareza em relações complexas) → Layout custom (o resto). Desça um degrau só quando o de cima ficar ilegível, nunca por hábito de XML. E lembre da regra de ouro do modelo: se você mede um filho, mede uma vez — guardar o Placeable e reusar, nunca measure() duas vezes.

Parte 4 · Estado: o coração do Compose

Um composable que lê um State vira reativo: quando o valor muda, ele recompõe. A pergunta que define tudo é onde esse estado mora — e disso depende quais eventos ele sobrevive.

@Composable
fun Contador() {
    // mutableStateOf cria um State observável; remember o preserva entre recomposições
    var n by remember { mutableStateOf(0) }
    Button(onClick = { n++ }) { Text("Cliquei $n vezes") }   // ler n aqui "assina" as mudanças
}

State hoisting: componente burro, dono esperto

O padrão-chave: ice o estado para fora do componente. Um composable stateless (recebe valor + lambda de evento) é reutilizável, testável e previsível. Quem segura o estado é o pai (ou o ViewModel).

// stateful: guarda o próprio estado — difícil de controlar/testar
@Composable fun CampoBusca() { var texto by remember { mutableStateOf("") } /* … */ }

// stateless (hoisted): estado DESCE, evento SOBE — a mesma ideia do UDF (art. 13)
@Composable
fun CampoBusca(texto: String, onTextoMuda: (String) -> Unit, modifier: Modifier = Modifier) {
    TextField(value = texto, onValueChange = onTextoMuda, modifier = modifier)
}

🧠 Termo — remember vs rememberSaveable: remember guarda o valor enquanto o composable estiver na árvore (sobrevive à recomposição, não ao giro de tela). rememberSaveable salva no Bundle e sobrevive à recriação da Activity — mas só serve para tipos “salváveis” (primitivos, Parcelable).

Parte 5 · As três fases de um frame

Para entender performance, você precisa saber o que o Compose faz a cada quadro. São três fases, e a chave é: cada uma pode ser pulada se a entrada dela não mudou.

🔒 Visão Specialist: a otimização mais poderosa do Compose é adiar a leitura do estado para a fase mais tardia. Modifier.offset { IntOffset(x, 0) } (lambda) lê a posição na fase de Layout; Modifier.offset(x.dp) (valor) lê na Composition. O primeiro anima sem recompor nada — o segundo recompõe a cada frame. Mesma API, custo brutalmente diferente.

Parte 6 · Recomposição inteligente e estabilidade

Recompor é re-executar funções @Composable. O Compose faz isso de forma cirúrgica: só os escopos que leram o estado alterado são refeitos; os irmãos são pulados (skipped) — desde que seus parâmetros sejam estáveis.

🧠 Termo — estabilidade / skipping: um tipo é estável se o Compose consegue saber quando ele mudou (imutável, ou notifica mudanças). Parâmetro estável e igual ao anterior ⇒ o Compose pula aquele composable. Tipos instáveis (uma List/Map comum, classes de outro módulo sem garantia) forçam recomposição “por via das dúvidas”.

// ❌ instável: List é interface mutável → o Compose não pode pular este composable
@Composable fun Lista(itens: List<Item>) { /* … */ }

// ✅ estável: marque o modelo e use coleções imutáveis (kotlinx.collections.immutable)
@Immutable
data class Item(val id: String, val titulo: String)
@Composable fun Lista(itens: ImmutableList<Item>) { /* … */ }

🔒 Visão Specialist: em 2026 o compilador do Compose tem strong skipping ligado por padrão, que pula composables mesmo com alguns parâmetros instáveis (comparando por instância) e lembra lambdas automaticamente. Isso reduz muito o problema — mas não substitui modelar dados imutáveis. Rode o compiler metrics para ver quais composables estão restartable mas não skippable: cada um desses é um suspeito de recomposição excessiva.

Parte 7 · Side-effects: falar com o mundo de fora

Uma função @Composable deve ser sem efeito colateral: ela pode rodar muitas vezes, em qualquer ordem, e ser cancelada. Então “rodar código de verdade” (chamar API, mostrar snackbar, iniciar animação) precisa de APIs de efeito que amarram o trabalho ao ciclo de vida da composição.

APIUse paraDispara quando
LaunchedEffect(key)rodar suspend ao entrar / quando a key mudaentra na composição ou key muda; cancela ao sair
rememberCoroutineScope()disparar corrotina a partir de um evento (clique)você chama, dentro de uma lambda
DisposableEffect(key)registrar/dar baixa em algo (listener, observer)entra; o onDispose{} roda ao sair
derivedStateOf { }estado calculado de outro, sem recompor à toasó quando o resultado derivado muda
snapshotFlow { }transformar State em Flowquando o State lido muda
 
@Composable
fun TelaPerfil(id: String, vm: PerfilViewModel) {
    // roda a busca ao abrir e SEMPRE que o id mudar; cancela sozinho ao sair da tela
    LaunchedEffect(id) { vm.carregar(id) }

    val listState = rememberLazyListState()
    // derivedStateOf: só recompõe o botão quando o booleano VIRA, não a cada pixel de scroll
    val mostrarTopo by remember {
        derivedStateOf { listState.firstVisibleItemIndex > 5 }
    }
    if (mostrarTopo) BotaoVoltarAoTopo()
}

⚠️ Pegadinha: nunca chame viewModel.carregar() solto no corpo do composable — ele rodaria a cada recomposição, disparando dezenas de chamadas. Trabalho com efeito vai sempre dentro de um LaunchedEffect/evento. E cuide da key: LaunchedEffect(Unit) roda uma vez; LaunchedEffect(id) re-roda quando o id muda.

Parte 8 · Performance: as regras que evitam jank

RegraPor quê
Adie a leitura de estadolambda no Modifier (offset{}, drawBehind{}) lê na fase tardia — anima sem recompor
Modelos imutáveis + @Immutabledeixa o Compose pular composables com segurança
key em LazyColumnidentidade estável ao reordenar/inserir — reusa itens certos
Nada de alocação pesada na composiçãoela roda muito; ordene/filtre em remember(entrada){…} ou no ViewModel
Baseline Profilespré-compila (AOT) o caminho crítico → primeira rolagem sem jank de JIT
Meça, não adivinheLayout Inspector (contagem de recomposição) + compiler metrics apontam o culpado

🔒 Visão Specialist: otimize depois de medir. O Compose em debug é enganosamente lento (sem R8, com asserts); toda medição de performance vale só em build release com Baseline Profile. A maioria do “jank” real vem de três coisas: recomposição excessiva por instabilidade, trabalho pesado dentro da composição, e listas sem key. Ataque nessa ordem.

Parte 9 · Animação: movimento sem recompor à toa

Animar no Compose é, na maioria das vezes, animar um estado — você troca o valor-alvo e o framework interpola. A dificuldade não é fazer mexer; é escolher a API certa e não pagar recomposição por frame. Comece sempre pela pergunta “o que está animando?”.

// 1) O caso comum: animar UM valor de estado — declarativo
val cor by animateColorAsState(if (ativo) Verde else Cinza, label = "cor")
val elevacao by animateDpAsState(if (pressionado) 8.dp else 2.dp, label = "elev")
Box(Modifier.background(cor))

// 2) Aparecer/sumir com transição de entrada e saída
AnimatedVisibility(visible = mostraDetalhe, enter = fadeIn() + expandVertically()) {
    Detalhe()
}

// 3) Vários valores coordenados por UM gatilho: updateTransition
val t = updateTransition(selecionado, label = "chip")
val borda by t.animateDp(label = "borda") { if (it) 2.dp else 0.dp }
val fundo by t.animateColor(label = "fundo") { if (it) RoxoClaro else Transparente }

// 4) Performance: anime na fase de layout/draw, NÃO recompondo
Box(Modifier.graphicsLayer { translationX = deslize }) // lê o estado na fase tardia

⚠️ Pegadinha: animar via Modifier.offset(x.dp) (valor) recompõe a cada frame; animar via Modifier.offset { IntOffset(x, 0) } ou graphicsLayer { } (lambda) só refaz a fase de layout/draw. Em animação contínua a diferença é jank vs. 120fps. E sempre dê um label — é o que o Animation Preview do Android Studio usa para inspecionar a curva.

🔒 Visão Specialist: não anime “porque fica bonito”. Movimento tem função — dizer de onde veio o novo conteúdo, guiar o olho, dar feedback de toque. Duração curta (~100–300ms), easing do Material, e respeite a preferência de reduzir movimento do sistema: encurte ou desligue quando o usuário pediu. Animação longa ou paralaxe agressiva é problema de acessibilidade, não charme.

Parte 10 · Efeitos visuais: sombra, gradiente, blur e Canvas

“Deixar bonito” no Compose é quase sempre um Modifier na fase de desenho — e como essa fase é a última (Parte 5), mudar aparência é barato: não recompõe nem refaz layout. Há quatro caixas de ferramentas.

// 1) graphicsLayer: transformar (o mais versátil) — ideal para animar
Box(Modifier.graphicsLayer {
    alpha = 0.9f; rotationZ = giro; scaleX = 1.1f
    shadowElevation = 8.dp.toPx(); clip = true; shape = CircleShape
})

// 2) moldar/contornar por shape (atalhos comuns)
Modifier.clip(RoundedCornerShape(12.dp))
Modifier.shadow(4.dp, RoundedCornerShape(12.dp)).border(1.dp, Cinza, RoundedCornerShape(12.dp))

// 3) pintar com Brush (gradiente) — funciona em background E em texto
val brush = Brush.linearGradient(listOf(Roxo, Azul))
Box(Modifier.background(brush))
Text("Nexus", style = TextStyle(brush = brush))

// 4) desenho custom quando nada pronto serve
Modifier.drawBehind {                    // DrawScope: você pinta na mão
    drawArc(Verde, -90f, progresso * 360f, useCenter = false, style = Stroke(6.dp.toPx()))
}
Modifier.blur(12.dp)                      // desfoque (fundo de diálogo, placeholder)

🧠 Termo — graphicsLayer: um modifier que aplica transformações (alpha, escala, rotação, translação, sombra, clip) desenhando o conteúdo numa camada separada. Como só afeta o desenho, animar por ele (versão lambda) não dispara recomposição — é o segredo de animação fluida. É também onde mora o compositingStrategy para efeitos que precisam da camada isolada (ex.: máscara com BlendMode).

⚠️ Pegadinha: Modifier.blur() e alguns RenderEffect só têm aceleração de hardware no Android 12+ — em versões antigas podem cair para um caminho lento ou não aplicar. E cuidado com sombra: shadow()/shadowElevation força uma camada de composição; espalhar sombra em centenas de itens de lista custa. Meça em release (Parte 8).

SubcomposeLayout e Modifier.Node são poderosos e caros de manter — cada um que você adiciona é código de framework que você passa a manter. Alcance-os por uma dor medida, nunca por curiosidade.
