🕶️ Encolher e ofuscar: R8, keep rules & ler crash em produção (2026)

No artigo 05 você marcou isMinifyEnabled = true e guardou o mapping.txt — sem entender direito o que aquilo fazia. Este artigo abre a caixa: o que o R8 faz com o seu código no build de release, por que ele às vezes quebra o app (e só no release), como consertar com keep rules, e como transformar um crash ofuscado da Play em uma linha que você consegue ler.

🔗 Fio condutor: o 05 tratou a ofuscação como um interruptor a ligar antes de publicar. Aqui vemos o que ele liga — e por que “funciona no debug, quebra no release” é, quase sempre, uma keep rule faltando.

O que é o R8

Quando você compila em release, o R8 entra entre o seu código e o .aab e faz quatro trabalhos numa passada só. O antecessor dele, o ProGuard, fazia parecido; hoje o R8 é o padrão do Android e usa a mesma sintaxe de regras.

EstágioO que fazGanho
Shrink (encolher)remove classes e métodos que ninguém chama (“tree shaking”)app menor — some o código morto das libs também
Optimize (otimizar)faz inline, funde classes, simplifica desviosapp um pouco mais rápido
Obfuscate (ofuscar)renomeia classes/métodos para a, b, cmenor ainda + mais chato de decompilar
Shrink de recursosapaga drawables, strings e layouts sem usomenos peso de res/
 
// build.gradle.kts (módulo :app)
android {
    buildTypes {
        release {
            isMinifyEnabled = true       // liga shrink + optimize + obfuscate
            isShrinkResources = true     // liga o shrink de recursos (precisa do de cima)
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"     // SUAS keep rules
            )
        }
    }
}

⚠️ Pegadinha: só escrever release no nome do build não liga nada. Sem isMinifyEnabled = true, seu app de loja vai grande, lento e sem ofuscação. E isShrinkResources exige o isMinifyEnabled ligado — senão o build falha.

Por que o app quebra (só no release)

O estágio de ofuscação renomeia tudo por baixo dos panos. Isso é invisível para código que chama método diretamente — o compilador atualiza a chamada junto. Mas quebra código que encontra classes por nome em texto, em tempo de execução: a reflexão.

🧠 Termo — reflexão: quando o programa procura uma classe/campo pelo nome em tempo de execução, em vez de chamar direto. Bibliotecas de JSON e banco fazem isso: leem "email" do JSON e procuram um campo chamado email na sua classe. Se o R8 renomeou email para b, a busca falha.

Como o debug não ofusca, o bug some no seu emulador e só aparece no .aab de produção — o pior lugar para descobri-lo. Os suspeitos de sempre:

Biblioteca / recursoPor que quebra
Gsoncasa campos do JSON pelo nome via reflexão
Retrofitlê anotações e tipos de retorno por reflexão
Roomas entidades precisam manter nomes de campo
Enums / classes de modeloserializados por nome; valueOf() usa o nome literal

Keep rules: a exceção controlada

Uma keep rule é uma linha no proguard-rules.pro que diz ao R8: “esta classe, não mexa”. É como você protege o que a reflexão precisa encontrar pelo nome original.

# proguard-rules.pro

# 1) Manter suas classes de modelo (as que viram JSON) intactas
-keep class com.nexus.data.model.** { *; }

# 2) Manter enums (o valueOf/name depende do nome literal)
-keepclassmembers enum * {
    public static **[] values();
    public static ** valueOf(java.lang.String);
}

# 3) Manter nomes de arquivo/linha no stacktrace (para o retrace funcionar)
-keepattributes SourceFile,LineNumberTable
-renamesourcefileattribute SourceFile

No dia a dia é ainda mais simples: anote a classe com @Keep e pronto — sem tocar no .pro:

import androidx.annotation.Keep

@Keep                      // R8 não renomeia nem remove esta classe
data class Usuario(val name: String, val email: String)

🔒 Visão Specialist: keep rule é bisturi, não machado. -keep class ** { *; } “resolve” tudo — e joga fora todo o ganho do R8, mantendo o app inteiro. Mantenha cada regra estreita (só o pacote de modelos, não o app todo). Melhor ainda: prefira o kotlinx.serialization ao Gson — ele gera o código de serialização em tempo de compilação e não usa reflexão, então dispensa quase todas as keep rules. Boas libs (Retrofit, Room, Moshi) já trazem as próprias regras — você raramente precisa escrever para elas.

🧠 Termo — consumer rules: quando você publica uma biblioteca, coloca as keep rules dela num consumer-rules.pro. Elas viajam junto com a lib e são aplicadas automaticamente no app que a usa — por isso você não precisa escrever regras para o Retrofit: ele já traz as dele.

Ler o crash de produção: o retrace

Com o app ofuscado, o relatório de crash da Play chega assim: at a.b.c(Unknown:0). Ilegível — de propósito. O mapping.txt daquele build é o dicionário que desfaz isso, e a ferramenta retrace aplica o dicionário no stacktrace:

# traduz o stacktrace ofuscado de volta para nomes reais
retrace  mapping.txt  crash-ofuscado.txt
# → at com.nexus.LoginViewModel.onClick(LoginViewModel.kt:42)

⚠️ Pegadinha: o mapping.txt é único por build. O da versão 1.2.0 não decodifica um crash da 1.3.0 — os nomes a, b são reatribuídos a cada compilação. Por isso a esteira do artigo 06 arquiva o mapping de toda release: sem o arquivo certo, o crash daquela versão é indecifrável para sempre.

🔒 Visão Specialist: na prática você não roda retrace à mão. Suba o mapping.txt para a Play Console (ela desofusca os crashes sozinha) ou para o seu monitor de erros (Crashlytics, Sentry) — a esteira faz esse upload no mesmo passo em que publica o .aab. O retrace manual fica para quando você tem só um log solto na mão.

Até onde a ofuscação protege

É tentador achar que ofuscar “esconde” o app. Protege um pouco — encarece a engenharia reversa —, mas não é segurança de verdade. Seja realista sobre o limite:

A ofuscação…Realidade
esconde a lógica do app?Atrapalha, não impede. Renomear login para a não apaga o que o método faz — um decompilador ainda lê o fluxo.
esconde chaves de API / segredos no código?Não. String hard-coded continua legível no APK. Segredo não vai no cliente — fica no servidor.
protege contra pirataria / adulteração?Fracamente. Para isso existem verificação de integridade (Play Integrity API), não a ofuscação.
reduz o tamanho do app?Sim — e esse é o ganho mais concreto e garantido no dia a dia.

🔒 Visão Specialist: trate o R8 como uma ferramenta de tamanho e performance que dá de brinde um obstáculo à cópia — não como um cadeado. Nada sensível (chave, senha, regra de negócio crítica) deve depender de estar “escondido” no cliente. Se precisa mesmo blindar o binário (fintech, DRM), aí entra ferramenta paga dedicada (ex.: DexGuard), fora do escopo do R8.
