🤖 Desenvolver Android com IA: o agente na sua bancada (2026)

Você já sabe montar a arquitetura (artigo 13) e testar cada camada (artigo 15) do NexusHub. Falta o operário que digita. Um agente de código — o Claude Code roda no terminal, dentro do seu repositório — lê seus arquivos, roda o ./gradlew, edita Kotlin e olha o resultado. Este artigo é a oficina: como conduzir esse operário sem torrar cota nem deixá-lo reescrever o app inteiro por conta própria.

🔗 Fio condutor: aqui você aprende a operar a IA; no artigo 17 aprende a dirigi-la por especificação (SDD, TDD, BDD). Tudo que você montou até agora — Gradle, arquitetura em camadas, pirâmide de testes — vira o contrato que mantém o agente honesto.

Chatbot responde. Agente age.

Um chatbot devolve texto. Um agente tem ferramentas: abre build.gradle.kts, roda ./gradlew testDebugUnitTest, aplica um diff, lê o stacktrace e tenta de novo. A pasta do projeto é a sua bancada: cada arquivo que ele lê entra na conversa e ocupa espaço. Por isso o pedido bom tem sempre a mesma forma: uma intenção, um artefato, um limite.

Pedido bomPedido caro
“Extraia a validação de e-mail de LoginViewModel para um UseCase. Só isso.”“Monta o app inteiro com login, Pix e tema, e me explica cada arquivo.”
Escopo fechado, um arquivo, dá para revisar o diff.O agente lê o mundo, gera centenas de linhas e você não consegue auditar.

🧠 Termo — agente: um LLM num laço com ferramentas (ler, editar, rodar comando). Ele não “sabe” seu projeto — ele descobre lendo, e leitura custa contexto.

Parte 1 · O loop e o custo do modelo

Você não paga só o que digitou. Paga cada volta do laço: ler, editar, olhar a saída, tentar de novo. Entender o loop é entender a conta.

O modelo é o ferro da peça, não o “melhor” da prateleira. Escolha pelo tamanho da ordem:

ModeloQuando usar no NexusHub
Haiku (rápido/barato)Tarefa mecânica: conferir um arquivo, renomear, rodar um checklist, resumir um log de build.
Sonnet (o dia a dia)O grosso do trabalho: implementar um Composable da spec, escrever testes de ViewModel, review simples.
Opus (raro)Recorte de arquitetura travado, um bug de corrotina que já quebrou duas vezes, refatoração de módulo inteiro.

🔒 Visão Specialist: não deixe Opus ligado por costume, e não troque de modelo no meio de uma janela gorda — o modelo novo herda todo o lixo do anterior. Grave o que vale num .md, abra sessão nova, escolha o modelo novo. Antes de um prompt largo, olhe o /usage: plano pago e API são torneiras diferentes.

⚠️ Pegadinha — o “continua” infinito: cada “continua, faz o resto” é uma volta com a janela inteira relida. Se a ordem foi cumprida, pare. Se faltou um detalhe, peça o detalhe — não “o resto”.

Parte 2 · Contexto: a janela é uma mochila

A janela de contexto é finita. Prompt do sistema, seu CLAUDE.md, skills disparadas, cada arquivo lido e todo o papo competem pelo mesmo espaço. Quando enche, as respostas pioram e ficam mais caras. Você tem três gestos para controlar o peso.

GestoQuando
Compactar /compactMesma ordem, agente no trilho, janela cheia. Compacte com foco: “fique só na tela de login, ignore o resto”.
Janela nova /clearAssunto mudou, papel mudou, agente preso, ou você precisa de outro modelo.
Compartilhar (gravar .md)O próximo papel — ou você amanhã — precisa do que foi decidido. Grava um arquivo; a sessão seguinte lê o arquivo.

🔒 Visão Specialist — compartilhar não é encaminhar o chat. Colar 80 linhas de conversa na próxima sessão enche a mochila de novo e a cópia não some quando o código muda. Deixe uma decisão gravada no disco (docs/DECISOES.md) e mande “leia o arquivo e continue”. O mesmo vale para código: nunca cole um Composable de 400 linhas — o agente lê o arquivo.

Parte 3 · Memória: o caderno na parede

Sessão nova, cabeça nova. O que precisa valer em toda sessão mora no CLAUDE.md, lido no arranque. Como ele viaja em cada conversa deste repo, cada linha custa — mantenha-o curto e permanente.

# NexusHub — regras do projeto

- App Android nativo: Kotlin + Jetpack Compose, minSdk 24, targetSdk 35.
- Arquitetura em camadas (ver artigo 13): domínio puro, sem Android no core.
- UI stateless + ViewModel com StateFlow (MVI). Sem lógica na @Composable.
- Injeção com Hilt. Nada de singleton manual.
- Textos de UI em português, via strings.xml (nunca hardcoded).
- Teste novo acompanha código novo (ver artigo 15).
- NÃO adicione dependência nova sem eu pedir.

🧠 Termo — duas memórias: o CLAUDE.md (você escreve, o time vê — regra de projeto) e a auto-memória (o agente anota a partir das suas correções; veja com /memory). A segunda é contexto, não lei.

⚠️ Pegadinha — o CLAUDE.md-romance: tutorial de Compose, histórico de decisões e a spec inteira não entram aqui — você pagaria por isso em cada sessão. Regra permanente fica no CLAUDE.md; detalhe sob demanda vira skill ou .md de apoio.

Parte 4 · Skills, comandos e MCP

Repetir o mesmo briefing em todo prompt é o vazamento mais caro. A saída é o progressive disclosure: carregar o detalhe só quando o pedido casa.

CamadaO que éCusto
Sempre ligadoCLAUDE.md — regras curtas do projeto.Viaja em toda sessão.
Sob demandaSkill: .claude/skills/*/SKILL.md. No arranque, só nome + descrição; o corpo entra quando a descrição casa com o pedido. Detalhe pesado em references/.Zero até disparar.
Peça cortada.md de apoio: docs/SPEC.md, um checklist. “Leia X e continue.”Só quando você manda ler.

Duas peças a mais que valem para o dev Android:

  • Slash commands — atalhos de prompt reutilizáveis em .claude/commands/. Ex.: um /revisar-pr que sempre roda lint + Detekt + testes e resume. O time inteiro padroniza a revisão.
  • MCP (Model Context Protocol) — servidores que dão ferramentas novas ao agente (abrir um board de tarefas, consultar o Sonar, ler o Crashlytics). É como o agente enxerga além do repositório, sem você colar dados na mão.
  • Subagente — o modelo delega uma tarefa pontual (uma busca pesada, uma leitura ampla) a outra janela, e só o resultado volta. Serve para não sujar a janela principal — não para misturar papéis.

🔒 Visão Specialist: se você digita “o app é Compose, MVI, Hilt, textos em pt-BR…” pela quinta vez, isso virou skill. Se a skill não dispara quando deveria, o problema está na description (o que/quando), não no corpo. Conserte a description.

Parte 5 · O squad de um dev só

PO, Tech Lead, UX/Dev e QA não são pessoas nem telas — são jeitos de usar o agente. Quando o tipo de trabalho muda, você troca de papel, de preferência em sessão nova, lendo o arquivo que o papel anterior deixou. Uma pessoa toca as quatro sessões; o bastão é um arquivo.

Por que separar, se é a mesma pessoa? Porque cada papel tem um foco e uma recusa. O PO não escreve Kotlin; o Tech não redesenha o produto; o Dev não reabre escopo; o QA não edita. Misturar tudo num chat “seja os quatro” faz o modelo agradar todos e entregar um app sem critério — e você acaba compactando lixo.

// Sessão do PO — jaleco de produto, não escreve código
Jaleco de PO. Não escreva código.
Leia README.md e CLAUDE.md.

Contexto: usuários precisam recuperar a senha sem abrir chamado.
Escreva docs/PLANO.md com: problema, quem usa, 3 histórias, fora de escopo.
Sem stack, sem tela. Máximo 40 linhas.

// ...sessão nova...

// Sessão do Tech — lê o plano, trava o "como"
Jaleco de Tech Lead. Não escreva UI.
Leia docs/PLANO.md e CLAUDE.md. Não mude o escopo.
Escreva docs/SPEC.md: contrato do UseCase, estados da tela (MVI),
erros possíveis, critérios de pronto. Máximo 50 linhas.

🔒 Visão Specialist: quatro sessões curtas custam menos que um chat “seja os quatro” inchando a janela. E o artefato de cada papel (PLANO.md → SPEC.md → código → REVIEW.md) é justamente o encadeamento SDD do próximo artigo. O avançado — um arquivo em .claude/agents/ por papel — só compensa quando o time repete o fluxo; o jaleco no prompt já resolve.

Parte 6 · Guardrails para código Android gerado por IA

A IA gera Kotlin plausível — que compila e parece certo — e às vezes está errado. O especialista não confia: ele cerca. Estes são os guard-rails específicos de Android.

RiscoGuarda
API alucinada — método de Compose que não existe, parâmetro inventado.O build é o juiz: ./gradlew assembleDebug reprova na hora. Peça para o agente compilar antes de dizer “pronto”.
API depreciada — o treino tem código antigo (onActivityResult, AsyncTask).Fixe a regra no CLAUDE.md (“use Activity Result API, corrotinas”) e confie no Lint/Detekt do artigo 11.
Quebra da Regra da Dependência — IA importa Android no domínio.A arquitetura do artigo 13 vira teste: um teste de arquitetura (Konsist/ArchUnit) barra o import proibido.
Diff gigante — impossível de revisar.Uma intenção por commit. Você lê o diff antes de aceitar; código que você não entende não entra.

🔗 Ligação: os guard-rails não são novos — são a esteira que você já montou. O CI do artigo 10 roda os testes em todo push; a qualidade do artigo 11 pega o cheiro; a arquitetura do 13 e os testes do 15 são a rede que segura a alucinação. A IA acelera quem já tem disciplina; ela amplifica a bagunça de quem não tem.

🔒 Visão Specialist: trate cada PR gerado por IA como PR de um júnior brilhante e apressado — revise o diff, exija o teste, questione a dependência nova. A responsabilidade pelo código que sobe é sua, não do modelo.
