🧪 Testes no Android: da pirâmide ao Robot Pattern (2026)

No artigo 13 você montou uma arquitetura em camadas. Agora vem a recompensa: cada camada daquele desenho vira um tipo de teste — e os mais valiosos rodam na JVM em milissegundos, sem emulador. Este artigo percorre como testar cada peça (domínio, dados, ViewModel, Compose) e fecha com um padrão que deixa os testes de UI limpos e escaláveis: o Robot Pattern + AAA.

🔗 Fio condutor: a testabilidade não é um esforço à parte — é a consequência da arquitetura do 13. Injeção de dependência vira fake; UI stateless vira teste de Compose; domínio puro vira JUnit sem Android. Aqui colhemos tudo isso.

Parte 1 · A pirâmide de testes

Nem todo teste custa igual. Você quer muitos testes baratos e rápidos, e pouquíssimos caros e lentos. Essa proporção é a pirâmide.

⚠️ Pegadinha — a pirâmide invertida: testar “tudo pela tela” gera uma suíte de horas que pisca (passa e falha sem o código mudar — os flaky tests). Teste de UI é caro; use-o só onde nada mais alcança.

O básico de configuração (JUnit5 + amigos)

dependencies {
    testImplementation(platform("org.junit:junit-bom:5.11.3"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testImplementation("io.mockk:mockk:1.13.13")                       // dublês
    testImplementation("app.cash.turbine:turbine:1.2.0")              // testar Flow
    testImplementation("org.jetbrains.kotlinx:kotlinx-coroutines-test:1.9.0")

    // Compose / UI
    testImplementation("org.robolectric:robolectric:4.14")           // Android na JVM
    androidTestImplementation("androidx.compose.ui:ui-test-junit4")
    debugImplementation("androidx.compose.ui:ui-test-manifest")
}
tasks.withType<Test> { useJUnitPlatform() }

Parte 2 · Testar cada camada

Cada camada do artigo 13 pede um estilo de teste. Do mais barato para o mais caro:

Domínio — o teste mais fácil que existe

Kotlin puro, sem Android. Um UseCase é uma função: entra dado, sai resultado.

class AplicarCupomTest {
    @Test fun `cupom de 10 por cento abate do total`() {
        val resultado = AplicarCupom()(total = 100.0, cupom = Cupom("OFF10", 0.10))
        assertEquals(90.0, resultado)
    }
}

Dados — fakes, Room in-memory e MockWebServer

Aqui você prova que o Repository combina as fontes certo — sem tocar na rede real nem num banco de verdade.

// Room de verdade, mas em memória (some ao fim do teste)
val db = Room.inMemoryDatabaseBuilder(context, AppDatabase::class.java)
    .allowMainThreadQueries().build()

// API falsa que responde JSON controlado
val server = MockWebServer().apply {
    enqueue(MockResponse().setBody("""{"id":1,"name":"Ana"}"""))
}

🧠 Termo — fake, mock, stub: substitutos da dependência real. Fake = implementação leve de verdade (um repositório que guarda numa lista). Stub = devolve respostas fixas. Mock = além disso, verifica como foi chamado. Regra: prefira fakes — eles não amarram o teste aos detalhes internos. A taxonomia completa e onde cada um entra na arquitetura estão na Parte 3, logo abaixo.

ViewModel — estado, corrotinas e Turbine

O teste mais valioso do app (a lógica de tela). Troque o repositório real por um fake e observe o StateFlow emissão a emissão com o Turbine.

class LoginViewModelTest {
    private val repo = FakeAuthRepository()
    private val vm = LoginViewModel(FazerLogin(repo))

    @Test fun `login com sucesso vai de Loading a Sucesso`() = runTest {
        vm.state.test {                              // Turbine
            assertEquals(false, awaitItem().carregando)   // estado inicial
            vm.aoEntrar("ana@x.com", "1234")
            assertEquals(true, awaitItem().carregando)    // durante
            assertEquals(false, awaitItem().carregando)   // fim
        }
    }
}

🔒 Visão Specialist: injete o CoroutineDispatcher no ViewModel em vez de usar Dispatchers.Main direto. No teste você passa um StandardTestDispatcher e o runTest controla o tempo virtual — sem isso, testes de corrotina piscam. Esse é o detalhe que separa uma suíte confiável de uma que “às vezes passa”.

Parte 3 · Test doubles: dummy, stub, fake, spy, mock

“Trocar a dependência real por uma de mentira” tem nome e tem cinco tipos — a taxonomia de Gerard Meszaros que Martin Fowler popularizou. Saber qual usar e onde é o que separa uma suíte que protege de uma que só atrapalha. O termo guarda-chuva para todos é test double (dublê de teste, como o dublê de cinema).

DublêO que fazExemplo no Android
Dummysó preenche um parâmetro obrigatório; nunca é chamadoum Analytics vazio que o construtor exige mas o teste ignora
Stubdevolve respostas enlatadas para o cenárioAPI que responde Erro(500) para testar o caminho de falha
Fake ⭐implementação de verdade, leve, com atalhoFakeAuthRepository que guarda numa MutableList
Spyreal/stub que grava como foi chamado (sem exigir)contar quantas vezes o Logger.log() rodou
Mockpré-programa e exige as chamadas certasverify { analytics.enviar("compra") } com MockK

Onde cada um encaixa na arquitetura (art. 13)

A escolha não é gosto — é o que você está provando e em que camada. O eixo que decide: você verifica estado (o valor que saiu) ou interação (a chamada que foi feita)?

Você testa…A dependência trocadaMelhor dublê
ViewModel (camada UI)o Repository / UseCaseFake do Repository (+ Stub pontual p/ erro)
UseCase (domínio)a interface de RepositoryFake ou Stub — é Kotlin puro, trivial
Repository (dados)as fontes (Room, API, DataStore)Fake de fonte, Room in-memory, MockWebServer
um efeito é a chamada em sianalytics, logger, trackerMock/Spy — aqui a interação é o comportamento
 
// FAKE (1ª escolha): implementação real e leve — o teste não sabe o "como" interno
class FakeAuthRepository : AuthRepository {
    var proximoErro: Throwable? = null                 // botão para simular falha
    private val salvos = mutableListOf<Usuario>()
    override suspend fun login(email: String, senha: String): Result<Usuario> =
        proximoErro?.let { Result.failure(it) }
            ?: Result.success(Usuario(email).also { salvos += it })
}

// MOCK (exceção): use quando o EFEITO é a interação — "disparou o analytics?"
@Test fun `compra confirmada dispara evento`() = runTest {
    val analytics = mockk<Analytics>(relaxed = true)     // MockK
    val vm = CheckoutViewModel(FakeCarrinho(), analytics)
    vm.confirmar()
    verify(exactly = 1) { analytics.enviar("compra_confirmada") }   // verifica a chamada
}

🧠 Termo — verificação de estado × de interação: testar estado é olhar o resultado (“o UiState virou Sucesso?”) — robusto, sobrevive a refatoração. Testar interação é olhar as chamadas (“chamou repo.login() uma vez?”) — frágil, quebra quando você reorganiza o interior. Prefira estado; reserve interação para quando a chamada externa é o efeito observável.

🔒 Visão Specialist: o conselho do Google (e do tio Bob) é “fakes, não mocks”. Mock verifica implementação — todo teste vira refém do jeito interno, e refatorar (sem mudar o comportamento) quebra dezenas de testes vermelhos falsos. Fake verifica comportamento — você reescreve o miolo e os testes continuam verdes porque o resultado é o mesmo. Regra prática: o dono da interface escreve o Fake dela e o coloca num módulo :core-testing (art. 13), reusável por todo mundo. Você escreve o Fake uma vez; escreveria o mesmo every/returns em cada teste com mock.

⚠️ Pegadinha: não faça mock de tipos que você não possui — nem de classes do Android (Context, SharedPreferences), nem de tipos de biblioteca. Mock desses amarra seu teste ao contrato interno de um código alheio que pode mudar. Para dependências do Android, use um Fake (um FakePreferences) ou o Robolectric (Parte 1), que roda o Android de verdade na JVM. Mock é para suas interfaces, e mesmo assim com parcimônia.

Parte 4 · Testar componentes Compose

A UI do Compose é testada por semântica — a mesma árvore que dá acessibilidade. O ritmo é sempre encontrar um nó → agir → verificar.

PassoAPIExemplo
EncontraronNodeWithText, onNodeWithContentDescription, onNodeWithTagonNodeWithTag("botao-entrar")
AgirperformClick, performTextInput, performScrollTo.performClick()
VerificarassertIsDisplayed, assertIsEnabled, assertTextEquals.assertIsEnabled()
 
class LoginContentTest {
    @get:Rule val compose = createComposeRule()

    @Test fun `botao entrar habilita apos preencher campos`() {
        compose.setContent { LoginContent(state = LoginUiState(), onEntrar = { _, _ -> }) }

        compose.onNodeWithText("Entrar").assertIsNotEnabled()
        compose.onNodeWithContentDescription("E-mail").performTextInput("ana@x.com")
        compose.onNodeWithContentDescription("Senha").performTextInput("1234")
        compose.onNodeWithText("Entrar").assertIsEnabled()
    }
}

🧠 Termo — testTag: uma etiqueta invisível (Modifier.testTag("...")) para o teste encontrar um nó sem depender do texto exato (que muda com tradução). Use tag quando o texto for volátil; use texto/descrição quando quiser testar o que o usuário realmente vê.

🔒 Visão Specialist — as duas estradas do Compose: o mesmo teste roda em duas velocidades. Com Robolectric (pasta src/test/) ele roda na JVM em segundos e entra em todo PR. Instrumentado (src/androidTest/) roda no emulador, pega renderização real e gestos, mas é lento — reserve para o fluxo crítico. Escrever a UI stateless (artigo 13) é o que permite testar sem subir rede.

Screenshot testing (o estado da arte)

Para pegar regressão visual (um padding que quebrou, o dark theme torto), há o teste de captura: a ferramenta renderiza o Composable, salva um PNG de referência e, no próximo PR, compara pixel a pixel.

🧠 Termo — Paparazzi / Roborazzi: bibliotecas de screenshot test que renderizam Compose na JVM (sem emulador). Geram a imagem “dourada” (referência) e falham o build se a tela mudar sem querer. É a rede de segurança do design system.

Parte 5 · Robot Pattern + AAA: testes de UI limpos

Um teste de UI cru mistura o que se testa com como se clica — e vira ilegível. Ao ler um teste, você quer entender o cenário, não os detalhes de onNodeWithText(...).performClick(). O Robot Pattern (de Jake Wharton) separa os dois papéis.

🧠 Termo — Robot Pattern: “O quê” (a classe de Teste) descreve o cenário de forma limpa; “Como” (a classe Robot) encapsula a conversa com o framework. Muda a UI? você ajusta só o Robot — os testes que o usam continuam iguais.

Casado com o AAA (Arrange–Act–Assert), o resultado é um teste que se lê como um caso de uso e um time padronizado sem esforço:

// Base que "induz" o time ao AAA (arrange/action/assert encadeados)
abstract class BaseRobot<T> {
    inline fun arrange(block: T.() -> Unit): T { block(this as T); return this }
    inline fun action(block: T.() -> Unit): T { block(this as T); return this }
    inline fun assert(block: T.() -> Unit) { block(this as T) }
}

// O "COMO": esconde o Compose Test dentro de métodos com nome de negócio
class MyScreenRobot(private val rule: ComposeContentTestRule) : BaseRobot<MyScreenRobot>() {
    fun setScreen()          = rule.setContent { MyScreen() }
    fun clickButton()        = rule.onNodeWithText("Clique para mudar o texto").performClick()
    fun assertTextCorrectly() = rule.onNodeWithText("Texto Modificado").assertExists()
}

// O "O QUÊ": o teste vira um caso de uso legível
class MyScreenTest {
    @get:Rule val rule = createComposeRule()

    @Test fun `texto muda apos clique`() {
        MyScreenRobot(rule)
            .arrange { setScreen() }
            .action  { clickButton() }
            .assert  { assertTextCorrectly() }
    }
}

🔗 Ligação: este padrão (e o exemplo acima) vêm do artigo “Robot Pattern, AAA e Compose Testing”, do Eduardo Lima. Vale a leitura para a motivação completa.

🔒 Visão Specialist: um Robot por tela, métodos com nome de negócio (fazerLogin(), não digitarNosDoisCampos()). Quando o design mudar o botão de lugar, você conserta um método e toda a suíte volta a passar. É o mesmo princípio da arquitetura: esconder o como volátil atrás de um o quê estável.

Parte 6 · Fechando com a esteira

Testes só valem se rodarem sozinhos, em todo PR. Os artigos anteriores já montaram esse encaixe:

  • Artigo 06: a esteira roda testDebugUnitTest em cada push e barra o merge se algo falhar.
  • Artigo 07: o Kover mede a cobertura e o Quality Gate do Sonar impede o PR de piorar — foque a régua no domínio e nos ViewModels, onde o teste é barato e o valor é alto.

🔒 Visão Specialist: cobertura é piso, não troféu. 60% com testes que verificam comportamento vale mais que 90% de testes que só executam linhas sem asserção. Meça cobertura onde ela sinaliza risco real (domínio, lógica de estado), não perseguindo 100% em getters e código de UI.
