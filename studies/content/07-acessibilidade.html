♿ Acessibilidade no Android: o app que todo mundo usa (2026)

Um app bonito que só funciona para quem enxerga bem, toca com precisão e lê letra miúda é um app quebrado para milhões de pessoas. Acessibilidade (a11y) é fazer a interface funcionar com leitor de tela, com fonte gigante, com pouca visão, com controle por teclado ou switch, com daltonismo. No Android há muitas diretrizes — por isso este é um artigo só delas — mas a boa notícia é que a maioria é barata quando feita desde o início e o Compose expõe tudo pela API de semântica. Além de ser o certo a fazer, é requisito de qualidade das lojas e, em muitos contextos, exigência legal.

🔗 Fio condutor: o 05 · Compose e o 06 · Material te deram componentes que já vêm acessíveis; aqui você aprende a não estragar isso e a cobrir os casos que a máquina não adivinha. O alvo de 48dp vem do 04 · Densidade; o teste de a11y fecha no 14 · Testes.

Parte 1 · Semântica: o que o leitor de tela realmente “vê”

O TalkBack (leitor de tela do Android) não enxerga pixels. Ele lê uma árvore paralela — a árvore de semântica — que cada composable preenche: um rótulo, um papel (botão? imagem?), um estado (selecionado? desabilitado?). Componentes do Material já preenchem isso; o seu trabalho é completar o que falta e agrupar o que deve ser lido junto.

// Ícone-only: SEM rótulo o TalkBack anuncia "botão" e pronto — inútil
IconButton(onClick = ::excluir) {
    Icon(Icons.Default.Delete, contentDescription = "Excluir tarefa")   // descreva a AÇÃO
}

// Imagem decorativa: passe null para o leitor PULAR (não poluir a leitura)
Icon(Icons.Default.Circle, contentDescription = null)

// Agrupar um card para ser lido como UMA unidade, na ordem certa
Row(Modifier.semantics(mergeDescendants = true) {}) {
    Avatar(foto, contentDescription = null)   // já descrito pelo texto ao lado
    Column { Text("Ana Souza"); Text("online agora") }
}

🧠 Termo — árvore de semântica: a representação da UI que serviços de acessibilidade consomem. Em Compose você a ajusta com o Modifier.semantics { } e com parâmetros como contentDescription. mergeDescendants = true funde os filhos num só nó focável — o card vira uma parada, não cinco.

O mesmo vale para “item selecionado” marcado apenas por uma cor de fundo: precisa de estado semântico e, de preferência, um segundo indício visual.

Parte 3 · Estado, papel e mudanças anunciadas

Componentes prontos já anunciam seu papel e estado; ao construir algo custom (um chip de seleção feito na mão, um card clicável), você precisa dizer ao leitor o que ele é e como está.

// Um item de lista selecionável feito à mão: informe papel + estado
@Composable
fun ItemSelecionavel(texto: String, selecionado: Boolean, onClick: () -> Unit) {
    Row(
        Modifier
            .clickable(onClick = onClick)
            .semantics {
                role = Role.RadioButton                       // o QUE é
                selected = selecionado                        // COMO está (TalkBack fala "selecionado")
                stateDescription = if (selecionado) "selecionado" else "não selecionado"
            }
    ) { RadioButton(selected = selecionado, onClick = null); Text(texto) }
}

// Mudança dinâmica importante (ex.: "3 itens no carrinho") deve ser LIDA sem foco
Text("$qtd itens", Modifier.semantics { liveRegion = LiveRegionMode.Polite })

🧠 Termo — liveRegion: marca um trecho cujas mudanças o TalkBack deve anunciar sozinho, sem o usuário navegar até lá (um contador que muda, uma mensagem de status). Polite espera a fala atual terminar; Assertive interrompe — use com parcimônia.

// Teste de Compose que trava a acessibilidade como contrato (art. 14 · Testes)
composeTestRule.onNodeWithContentDescription("Excluir tarefa").assertIsDisplayed()
composeTestRule.onNode(hasContentDescription("Ligar para Ana")).assertHasClickAction()

🔒 Visão Specialist: a métrica que separa amador de sênior é navegar o app inteiro só com o TalkBack, de olhos fechados. Se você não consegue completar o fluxo principal, nenhum usuário de leitor de tela consegue. Faça isso uma vez por fluxo crítico — encontra em 5 minutos o que scanner automático nunca pega (rótulos que existem mas não fazem sentido, ordem que confunde). Acessibilidade boa também melhora SEO de app, testes de UI (nós têm rótulo) e a legibilidade para todos sob sol forte ou cansaço.
