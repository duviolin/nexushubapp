🧱 Padrões de projeto no Android: do GoF ao MVI (2026)

No artigo 09 · Arquitetura montamos as camadas; aqui descemos um nível e olhamos os tijolos: os padrões de projeto que aparecem repetidos dentro de cada camada. Padrão não é código pronto para copiar — é um nome para uma solução que já se provou. Saber o nome muda a conversa de equipe: em vez de “aquela classe que monta o objeto passo a passo” você diz “é um Builder”, e todo mundo já sabe a forma, as vantagens e as pegadinhas. Num nível especialista, você não decora os 23 padrões do GoF — você reconhece quais o próprio Android SDK já usa por baixo, e escolhe o certo sem reinventar.

🔗 Fio condutor: o 09 desenhou onde o código mora (camadas); este mostra com que formas ele se organiza dentro delas. Os dois juntos são o vocabulário que o 11 · Testes assume conhecido.

🧠 Termo — GoF (Gang of Four): os quatro autores do livro Design Patterns (1994), que catalogaram 23 padrões em três famílias — criacionais (como um objeto nasce), estruturais (como objetos se compõem) e comportamentais (como objetos conversam).

Parte 1 · Padrões de apresentação: a linhagem MVC → MVP → MVVM → MVI

Antes dos padrões “pequenos”, o padrão grande que rege a tela. Toda a história desses padrões de apresentação é uma pergunta só: onde mora o estado da tela? Cada geração tira estado e lógica de dentro da View e os empurra para um lugar mais testável e mais resistente ao ciclo de vida do Android.

PadrãoOnde mora o estadoDor que resolveDor que deixa
MVCna View + Activitysepara dado de desenho, na teoriano Android a Activity é View e Controller: acopla tudo
MVPno PresenterPresenter puro, testável sem UIuma interface View por tela — muito boilerplate
MVVMno ViewModel (vários observables)ViewModel sobrevive ao giro de tela; sem interface manualestado espalhado em N campos que podem divergir
MVIno ViewModel (um UiState)um estado imutável, fluxo unidirecional, reprodutívelmais cerimônia: Intent, reducer, canal de efeitos

🧠 Termo — “Model-View-*”: em todos, o Model é a mesma coisa (dados + regras: Repository/UseCase do artigo 09). O que muda é o pedaço do meio — Presenter, ViewModel — e a direção em que a informação corre.

MVVM × MVI, lado a lado

Na prática, hoje 99% dos apps Android são MVVM (o ViewModel do Jetpack já entrega o padrão de graça). A dúvida real do especialista é: meu ViewModel expõe vários observables (MVVM “clássico”) ou um único estado imutável (MVI)? Não são rivais — MVI é o MVVM levado ao extremo da disciplina de estado.

// ── MVVM clássico: um campo observável por pedaço da tela ──
class LoginViewModelMvvm : ViewModel() {
    val nome = MutableStateFlow("")
    val carregando = MutableStateFlow(false)
    val erro = MutableStateFlow<String?>(null)
    // 3 fluxos → a View combina 3 coletas; podem divergir no tempo
}

// ── MVI: UM estado imutável descreve a tela inteira ──
data class LoginUiState(
    val nome: String = "",
    val carregando: Boolean = false,
    val erro: String? = null,
)

sealed interface LoginIntent {                 // o EVENTO como objeto (Command)
    data class NomeMudou(val v: String) : LoginIntent
    data object Entrar : LoginIntent
}

class LoginViewModelMvi(private val fazerLogin: FazerLogin) : ViewModel() {
    private val _state = MutableStateFlow(LoginUiState())
    val state: StateFlow<LoginUiState> = _state.asStateFlow()   // 1 fonte da verdade

    fun onIntent(i: LoginIntent) = when (i) {                   // o reducer
        is LoginIntent.NomeMudou -> _state.update { it.copy(nome = i.v) }
        LoginIntent.Entrar       -> entrar()
    }
    private fun entrar() { /* chama o UseCase e faz _state.update { … } */ }
}

🔒 Visão Specialist: o divisor de águas é o estado impossível. No MVVM com campos soltos, nada impede carregando = true e erro != null ao mesmo tempo — um bug de tela que só aparece no timing certo. No MVI, como o estado é um objeto só montado por um reducer, você consegue modelar “ou carrega, ou deu erro, ou tem dado” com uma sealed interface e o compilador proíbe a combinação inválida. Vale a cerimônia extra em telas com muitos estados; em tela boba (um formulário simples) o MVVM enxuto basta.

⚠️ Pegadinha: não coloque eventos de uma vez só (navegar, mostrar snackbar) dentro do UiState. Estado é o que a tela é agora; navegar é algo que acontece uma vez. Se virar campo do estado, ao girar a tela o Compose relê o estado e navega de novo. Use um canal à parte (Channel/SharedFlow de efeitos) — a seta laranja do diagrama.

Parte 2 · Criacionais: como um objeto nasce

Agora os padrões “pequenos”. A boa notícia: o Android SDK é feito deles — você já os usa sem perceber. Ver o padrão por trás da API é o que permite estender ou testar com segurança.

Builder — montar passo a passo, construir no fim

O padrão que você mais vê no Android. Em vez de um construtor com 12 parâmetros na ordem exata, você encadeia .setX() — cada um devolve this — e só materializa o objeto (imutável) no .build().

🔒 Visão Specialist: em Java o Builder é quase obrigatório para objetos com muitos campos opcionais. Em Kotlin, argumentos nomeados + valores default resolvem o mesmo problema sem escrever a classe Builder — então não crie um Builder à mão para suas data class. Você ainda consome Builders o tempo todo (Retrofit, OkHttp, Notification) porque essas APIs precisam ser compatíveis com Java.

Factory Method & Abstract Factory — delegar “qual classe instanciar”

Factory Method: um método que decide qual objeto criar, escondendo o new/construtor de quem chama. LayoutInflater.from(context) te devolve um inflater sem você saber a classe concreta. Abstract Factory sobe um degrau: cria famílias de objetos que combinam entre si — é exatamente o que um módulo Hilt faz ao prover o grafo de dependências coerente.

// Factory Method na prática: você precisa criar um ViewModel com argumentos
class LoginVmFactory(private val useCase: FazerLogin) : ViewModelProvider.Factory {
    override fun <T : ViewModel> create(modelClass: Class<T>): T =
        LoginViewModel(useCase) as T   // a fábrica sabe montar; a tela só pede
}
// Com Hilt, @HiltViewModel + @Inject faz essa fábrica sumir — a DI É a fábrica.

O Abstract Factory não cria um objeto, mas uma família coerente deles. Um @Module do Hilt é isso: ele sabe montar o OkHttpClient, o Retrofit que depende dele e a Api que depende do Retrofit — tudo combinando.

// Abstract Factory: um módulo provê uma FAMÍLIA de objetos que se encaixam
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton
    fun client(): OkHttpClient = OkHttpClient.Builder().build()

    @Provides @Singleton
    fun retrofit(client: OkHttpClient): Retrofit =        // recebe o membro anterior
        Retrofit.Builder().baseUrl(BASE).client(client).build()

    @Provides
    fun api(retrofit: Retrofit): AuthApi = retrofit.create(AuthApi::class.java)
}

Singleton — uma instância para o app inteiro

Uma única instância compartilhada: o banco Room, o OkHttpClient (caro de criar), o DataStore. Em Kotlin, object já é um Singleton thread-safe pronto — mas a forma que você vai usar de verdade é a anotação @Singleton do Hilt.

// Singleton "cru" da linguagem: bom para constantes/utilitários SEM estado
object Formatadores {
    val moeda = NumberFormat.getCurrencyInstance()
}

// Singleton de verdade no app: uma instância, porém INJETÁVEL (testável)
@Singleton
class SessaoUsuario @Inject constructor() {           // o Hilt garante 1 só
    var token: String? = null
}

⚠️ Pegadinha: Singleton feito à mão vira estado global — difícil de testar (não dá para trocar por um fake) e memory-leak fácil se segurar um Context de Activity. A forma sênior é não escrever o Singleton: declare @Singleton no Hilt e deixe o container garantir a instância única e injetável. Você ganha o ciclo de vida certo e a testabilidade.

Parte 3 · Estruturais: como objetos se compõem

PadrãoIdeia em uma linhaOnde no Android
Adaptertradutor entre duas interfaces incompatíveisRecyclerView.Adapter: liga sua List ao formato que a lista exige
Facadeuma porta simples para um subsistema complexoRepository: a UI pede dado; não sabe se veio de Room ou Retrofit
Decoratorembrulha um objeto e adiciona comportamento sem herançaModifier do Compose e Interceptor do OkHttp encadeados

O Facade é o Repository que você já monta: uma porta única que esconde Room, Retrofit e cache. O Adapter traduz seus dados para o formato que um componente externo exige — o exemplo canônico é a lista.

// Facade: a UI chama UM método; o subsistema (cache + rede) fica escondido
class NoticiaRepository(private val api: NoticiaApi, private val dao: NoticiaDao) {
    fun observar(): Flow<List<Noticia>> = dao.observar()      // fonte da verdade: cache
    suspend fun atualizar() {                                   // detalhe escondido
        val frescas = api.buscar().map { it.toEntity() }        // rede + mapper
        dao.substituir(frescas)                                 // grava; a UI nem sabe
    }
}

// Adapter: traduz sua List<Noticia> para o que o RecyclerView entende
class NoticiaAdapter : ListAdapter<Noticia, NoticiaVH>(Diff) {
    override fun onCreateViewHolder(p: ViewGroup, v: Int) =
        NoticiaVH(ItemNoticiaBinding.inflate(LayoutInflater.from(p.context), p, false))
    override fun onBindViewHolder(vh: NoticiaVH, pos: Int) = vh.bind(getItem(pos))
}

O Decorator merece atenção porque o Compose o transformou no dia a dia. Cada Modifier embrulha o anterior, formando uma cadeia — e a ordem importa:

// Decorator: cada Modifier embrulha o de cima. Ordem = comportamento.
Modifier
    .padding(16.dp)          // 1º afasta…
    .background(Azul)        // 2º …depois pinta o fundo (só a área interna)

Modifier
    .background(Azul)        // 1º pinta tudo…
    .padding(16.dp)          // 2º …e o padding vira margem interna do fundo
// Mesmos dois modifiers, resultado visual diferente — é a cadeia de Decorators.

Parte 4 · Comportamentais: como objetos conversam

É a família mais presente na arquitetura reativa moderna. O Observer é literalmente a fundação do UDF do artigo 09: Flow/StateFlow são o padrão Observer — um sujeito (o ViewModel) notifica observadores (a UI) quando o estado muda, sem conhecê-los.

PadrãoIdeia em uma linhaOnde no Android
Observeravisa interessados quando algo mudaFlow, StateFlow, LiveData — a base de todo reativo
Strategyalgoritmo intercambiável passado de forapassar uma lambda de comparação/ordenação; trocar em runtime
Stateo objeto muda de comportamento conforme seu estadosealed interface UiState { Loading; Success; Error }
Commandencapsular uma ação como objeto (enfileirar, desfazer)Intent do MVI; tarefas do WorkManager
Chain of Responsibilityuma fila de handlers; cada um trata ou repassaa cadeia de Interceptors do OkHttp (auth → cache → log)

O Observer e o State são o par que rege a tela. O ViewModel emite um estado (Observer); esse estado é uma sealed interface que muda o que a UI desenha (State) — e o when exaustivo garante que você tratou todos os casos.

// State: os estados possíveis são finitos e mutuamente exclusivos
sealed interface TelaState {
    data object Carregando : TelaState
    data class Sucesso(val itens: List<Noticia>) : TelaState
    data class Erro(val msg: String) : TelaState
}

// Observer: a UI se inscreve e reage; o when é exaustivo (o compilador cobra)
@Composable
fun Tela(vm: TelaViewModel) {
    val estado by vm.state.collectAsStateWithLifecycle()   // observa o StateFlow
    when (val e = estado) {
        TelaState.Carregando -> Spinner()
        is TelaState.Sucesso -> Lista(e.itens)
        is TelaState.Erro    -> MensagemErro(e.msg)
    }
}

O Strategy em Kotlin quase desaparece: onde o GoF criava uma interface e várias classes, uma função de ordem superior (lambda) já é a estratégia. Isso é o padrão idiomático — reconhecê-lo evita criar uma hierarquia de classes onde uma lambda basta.

// Strategy "clássico": interface + implementações (verboso)
interface Ordenacao { fun aplicar(l: List<Tarefa>): List<Tarefa> }

// Strategy idiomático em Kotlin: a estratégia É uma lambda
fun listar(tarefas: List<Tarefa>, ordenar: (List<Tarefa>) -> List<Tarefa>) =
    ordenar(tarefas)

listar(tarefas) { it.sortedBy(Tarefa::prazo) }      // troca a estratégia na chamada
listar(tarefas) { it.sortedByDescending(Tarefa::prioridade) }

O Command transforma uma ação em objeto — assim ela pode ser enfileirada, repetida ou desfeita. No MVI, o Intent já é um Command; no trabalho em segundo plano, o WorkManager guarda o Command e o executa depois, mesmo se o app morrer. E a Chain of Responsibility é a cadeia de Interceptors do OkHttp: cada elo trata sua parte (autenticar, logar) e repassa ao próximo com chain.proceed().

// Command: a ação vira um objeto agendável (roda depois, sobrevive ao app fechar)
val enviar = OneTimeWorkRequestBuilder<EnviarPedidoWorker>()
    .setConstraints(Constraints(requiredNetworkType = CONNECTED))
    .build()
WorkManager.getInstance(ctx).enqueue(enviar)          // enfileira o Command

// Chain of Responsibility: cada interceptor trata o seu e chama chain.proceed()
class AuthInterceptor(private val sessao: SessaoUsuario) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val req = chain.request().newBuilder()
            .apply { sessao.token?.let { header("Authorization", "Bearer $it") } }
            .build()
        return chain.proceed(req)                     // repassa ao próximo elo
    }
}

Quando (não) usar um padrão

SituaçãoFaça
API Java com muitos campos opcionaisBuilder — ou, se for sua data class Kotlin, argumentos nomeados
Precisa de uma instância única e injetávelSingleton via Hilt (@Singleton), não object com Context
Trocar um algoritmo em runtimeStrategy como lambda, sem hierarquia de classes
Tela com poucos estados possíveisMVVM enxuto; não pague a cerimônia do MVI completo
Tela com muitos estados que não podem coexistirMVI + sealed UiState para o compilador barrar o impossível
“Vi um padrão que encaixa em qualquer lugar”Pare. Padrão a mais é acoplamento e indireção sem retorno

🔒 Visão Specialist: o erro de sênior júnior é patternitis — aplicar padrão por status, não por necessidade. Padrão bom remove uma dor concreta (um construtor ilegível, um algoritmo que muda, um estado que diverge). Se você não consegue nomear a dor que ele resolve aqui, a solução mais simples (uma função, uma data class, uma lambda) é a certa. Kotlin dissolve metade do GoF em recursos da linguagem — reconhecer isso é o nível especialista de verdade.
