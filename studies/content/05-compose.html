🎨 Jetpack Compose: a UI como função do estado (2026)

Até aqui a trilha cuidou do chão da UI — desenhar sob as barras (03), dp e densidade (04). Agora entra a ferramenta com que você realmente constrói tela no Android moderno: o Jetpack Compose. Ele troca o velho jeito imperativo (inflar XML, achar View por id e mandar cada mudança na mão) por um jeito declarativo: você descreve como a tela deve ficar para um dado estado, e o Compose se encarrega de atualizar o que mudou. Este artigo vai do básico (composables, layout, Modifier, estado) ao avançado (recomposição, estabilidade, side-effects e performance) — porque é fácil escrever Compose que funciona e difícil escrever Compose que não trava.

🔗 Fio condutor: o 04 · Densidade deu as unidades (dp); aqui você monta a tela com elas. O próximo (06 · Material 3) veste esses composables com o sistema de design, e o 12 · Arquitetura mostra quem alimenta o estado que a tela desenha.

Parte 1 · Declarativo: a virada de chave

No mundo antigo (Views/XML) a UI é um objeto que você muta: textView.text = "Oi", button.isEnabled = false. O bug clássico é a tela e os dados saírem de sincronia — você esqueceu de atualizar um dos dez lugares. No Compose, você não muta a tela: você escreve uma função que, dado o estado, produz a UI. Mudou o estado? O Compose re-executa a função e reconcilia a diferença.

// Imperativo (Views): você descreve os PASSOS de mudança
nomeTextView.text = usuario.nome
avatarImageView.setImageUrl(usuario.foto)
badge.visibility = if (usuario.online) View.VISIBLE else View.GONE

// Declarativo (Compose): você descreve o RESULTADO para aquele estado
@Composable
fun CartaoUsuario(usuario: Usuario) {
    Column {
        Text(usuario.nome)
        Avatar(usuario.foto)
        if (usuario.online) Badge()      // não existe "esconder": ou está na árvore, ou não
    }
}

🧠 Termo — @Composable: uma função anotada que emite UI em vez de retornar valor. Ela não “desenha” na hora: descreve um nó na árvore de UI que o Compose gerencia. Só pode ser chamada de dentro de outra função @Composable.

Parte 2 · Os blocos de construção

Três containers resolvem 90% do layout — e todos empilham por ordem de chamada:

ComposableFazEquivalente mental
Columnempilha os filhos na verticaluma pilha de cima para baixo
Rowalinha os filhos na horizontaluma fila lado a lado
Boxempilha os filhos em camadas (z)um FrameLayout: um sobre o outro
LazyColumn/LazyRowlista que só compõe o que está visívelo RecyclerView, sem boilerplate

O Modifier é o que ajusta tamanho, espaçamento, clique, fundo, borda — encadeado, e a ordem importa (é o padrão Decorator do artigo 13). Sempre receba um Modifier como parâmetro para o chamador poder posicionar seu componente.

@Composable
fun Saudacao(nome: String, modifier: Modifier = Modifier) {   // convenção: modifier é o 1º opcional
    Text(
        text = "Olá, $nome",
        modifier = modifier
            .fillMaxWidth()
            .padding(16.dp)          // afasta ANTES…
            .background(Azul)        // …então pinta só a área interna
            .clickable { /* … */ }
    )
}

// Lista performática: dê uma key estável para o Compose reusar os itens certos
@Composable
fun ListaTarefas(tarefas: List<Tarefa>) {
    LazyColumn {
        items(tarefas, key = { it.id }) { tarefa ->    // key evita recomposição errada ao reordenar
            LinhaTarefa(tarefa)
        }
    }
}

⚠️ Pegadinha: Column (e Row) compõem todos os filhos de uma vez — se a lista for grande, trava. Para listas roláveis use sempre LazyColumn: ela só compõe os itens na viewport. Column com verticalScroll é para conteúdo curto e conhecido.

Parte 3 · Estado: o coração do Compose

Um composable que lê um State vira reativo: quando o valor muda, ele recompõe. A pergunta que define tudo é onde esse estado mora — e disso depende quais eventos ele sobrevive.

@Composable
fun Contador() {
    // mutableStateOf cria um State observável; remember o preserva entre recomposições
    var n by remember { mutableStateOf(0) }
    Button(onClick = { n++ }) { Text("Cliquei $n vezes") }   // ler n aqui "assina" as mudanças
}

State hoisting: componente burro, dono esperto

O padrão-chave: ice o estado para fora do componente. Um composable stateless (recebe valor + lambda de evento) é reutilizável, testável e previsível. Quem segura o estado é o pai (ou o ViewModel).

// stateful: guarda o próprio estado — difícil de controlar/testar
@Composable fun CampoBusca() { var texto by remember { mutableStateOf("") } /* … */ }

// stateless (hoisted): estado DESCE, evento SOBE — a mesma ideia do UDF (art. 12)
@Composable
fun CampoBusca(texto: String, onTextoMuda: (String) -> Unit, modifier: Modifier = Modifier) {
    TextField(value = texto, onValueChange = onTextoMuda, modifier = modifier)
}

🧠 Termo — remember vs rememberSaveable: remember guarda o valor enquanto o composable estiver na árvore (sobrevive à recomposição, não ao giro de tela). rememberSaveable salva no Bundle e sobrevive à recriação da Activity — mas só serve para tipos “salváveis” (primitivos, Parcelable).

Parte 4 · As três fases de um frame

Para entender performance, você precisa saber o que o Compose faz a cada quadro. São três fases, e a chave é: cada uma pode ser pulada se a entrada dela não mudou.

🔒 Visão Specialist: a otimização mais poderosa do Compose é adiar a leitura do estado para a fase mais tardia. Modifier.offset { IntOffset(x, 0) } (lambda) lê a posição na fase de Layout; Modifier.offset(x.dp) (valor) lê na Composition. O primeiro anima sem recompor nada — o segundo recompõe a cada frame. Mesma API, custo brutalmente diferente.

Parte 5 · Recomposição inteligente e estabilidade

Recompor é re-executar funções @Composable. O Compose faz isso de forma cirúrgica: só os escopos que leram o estado alterado são refeitos; os irmãos são pulados (skipped) — desde que seus parâmetros sejam estáveis.

🧠 Termo — estabilidade / skipping: um tipo é estável se o Compose consegue saber quando ele mudou (imutável, ou notifica mudanças). Parâmetro estável e igual ao anterior ⇒ o Compose pula aquele composable. Tipos instáveis (uma List/Map comum, classes de outro módulo sem garantia) forçam recomposição “por via das dúvidas”.

// ❌ instável: List é interface mutável → o Compose não pode pular este composable
@Composable fun Lista(itens: List<Item>) { /* … */ }

// ✅ estável: marque o modelo e use coleções imutáveis (kotlinx.collections.immutable)
@Immutable
data class Item(val id: String, val titulo: String)
@Composable fun Lista(itens: ImmutableList<Item>) { /* … */ }

🔒 Visão Specialist: em 2026 o compilador do Compose tem strong skipping ligado por padrão, que pula composables mesmo com alguns parâmetros instáveis (comparando por instância) e lembra lambdas automaticamente. Isso reduz muito o problema — mas não substitui modelar dados imutáveis. Rode o compiler metrics para ver quais composables estão restartable mas não skippable: cada um desses é um suspeito de recomposição excessiva.

Parte 6 · Side-effects: falar com o mundo de fora

Uma função @Composable deve ser sem efeito colateral: ela pode rodar muitas vezes, em qualquer ordem, e ser cancelada. Então “rodar código de verdade” (chamar API, mostrar snackbar, iniciar animação) precisa de APIs de efeito que amarram o trabalho ao ciclo de vida da composição.

APIUse paraDispara quando
LaunchedEffect(key)rodar suspend ao entrar / quando a key mudaentra na composição ou key muda; cancela ao sair
rememberCoroutineScope()disparar corrotina a partir de um evento (clique)você chama, dentro de uma lambda
DisposableEffect(key)registrar/dar baixa em algo (listener, observer)entra; o onDispose{} roda ao sair
derivedStateOf { }estado calculado de outro, sem recompor à toasó quando o resultado derivado muda
snapshotFlow { }transformar State em Flowquando o State lido muda
 
@Composable
fun TelaPerfil(id: String, vm: PerfilViewModel) {
    // roda a busca ao abrir e SEMPRE que o id mudar; cancela sozinho ao sair da tela
    LaunchedEffect(id) { vm.carregar(id) }

    val listState = rememberLazyListState()
    // derivedStateOf: só recompõe o botão quando o booleano VIRA, não a cada pixel de scroll
    val mostrarTopo by remember {
        derivedStateOf { listState.firstVisibleItemIndex > 5 }
    }
    if (mostrarTopo) BotaoVoltarAoTopo()
}

⚠️ Pegadinha: nunca chame viewModel.carregar() solto no corpo do composable — ele rodaria a cada recomposição, disparando dezenas de chamadas. Trabalho com efeito vai sempre dentro de um LaunchedEffect/evento. E cuide da key: LaunchedEffect(Unit) roda uma vez; LaunchedEffect(id) re-roda quando o id muda.

🔒 Visão Specialist: otimize depois de medir. O Compose em debug é enganosamente lento (sem R8, com asserts); toda medição de performance vale só em build release com Baseline Profile. A maioria do “jank” real vem de três coisas: recomposição excessiva por instabilidade, trabalho pesado dentro da composição, e listas sem key. Ataque nessa ordem.
